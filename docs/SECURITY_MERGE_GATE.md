# Security Merge Gate: M1 (Identity, Courses, Ownership)

**Purpose:** the release gate for backend milestone M1. M1 may be marked complete, and merged, only when **every item
below passes** in CI on the merge commit.
**Authority:** derived from [`backend_security_contract.md`](backend_security_contract.md) (the contract). Rule ids
(`OWN-03`, `JWT-05`, `RT-05`, ...) refer to it; matrix ids (`I-01`, `A-05`, ...) refer to its section 10. If this
gate and the contract disagree, the contract wins and this file is corrected.
**Version:** 1.0, 2026-11-24 (before M1 implementation).

## 1. Gate rules

1. Every gate item has an automated test. Test names start with the gate id in lower case, e.g.
   `test_g1_iso_01_...`, so CI output maps one to one onto this table.
2. A gate item passes only if its test passes **without skips** on the merge commit, in the CI workflow
   (`.github/workflows/backend.yml`, all jobs green: secret scan, dependency audit, lint, types, tests).
3. No item may be waived. Changing an expected result requires a contract change first (contract section 0).
4. "Same 404" means: status 404, `Content-Type: application/problem+json`, and a body identical to the body returned
   for a random, never-issued UUID, except for `request_id`.
5. "Generic 401" means: status 401, header `WWW-Authenticate: Bearer`, and one body shared by every token failure;
   the body never names the failed check (JWT-09).
6. M0 gates stay gates: section 9 lists the M0 checks that must still pass.

## 2. Scope of M1 (what the gate covers)

| Area | Endpoints / components |
|---|---|
| Registration and login | `POST /api/v1/auth/register`, `POST /api/v1/auth/login` |
| Session | `POST /api/v1/auth/refresh`, `POST /api/v1/auth/logout`, `POST /api/v1/auth/logout-all`, `GET /api/v1/auth/me` |
| Password | `POST /api/v1/auth/change-password` (needed to prove token revocation, JWT-05 / RT-06) |
| Courses | `POST /api/v1/courses`, `GET /api/v1/courses`, `GET /api/v1/courses/{id}`, `PATCH /api/v1/courses/{id}` (rename / archive), `DELETE /api/v1/courses/{id}` |
| Components | `users`, `refresh_tokens`, `courses` tables and migration; Argon2id hashing; JWT issue/verify; refresh-token store; lockout; rate limits on auth routes; the ownership helper `get_owned` |

**Fixture used throughout:** two registered, active users **A** and **B** (role `STUDENT`), each with one course
(`A_course`, `B_course`); a third user **C** with role `ADMIN`; a clock that tests can advance.

## 3. Cross-user isolation

| ID | Test case | Expected result | Rules |
|---|---|---|---|
| G1-ISO-01 | B sends `GET /courses/{A_course}` | Same 404; A's course unchanged; security event `ownership_mismatch` logged with B's user id, resource type `course`, id `A_course` | OWN-03, OWN-04, OWN-05 (I-01) |

| G1-ISO-04 | B sends `GET /courses` | Response lists exactly B's courses; no field, count or pagination total reveals A's courses | OWN-07 (I-03) |
| G1-ISO-05 | A and B each create a course with the same name and code | Both succeed with different ids; each sees only their own | OWN-02, OWN-07 |
| G1-ISO-06 | B's access token used on every course route with A's id, in one parametrised test | Same 404 for all; no 403 anywhere | OWN-04 |
| G1-ISO-07 | `GET /auth/me` with B's token | Returns B's profile only; no field from A; no password hash, lockout counters or token data in the body | OWN-03, SEC-01 |
| G1-ISO-08 | A's refresh cookie presented together with B's access token on `/auth/refresh` | The new session belongs to A (cookie owner), never to B; B's session unaffected | RT-04 |

## 7. Refresh-token rotation and revocation

| ID | Test case | Expected result | Rules |
|---|---|---|---|
| G1-RT-01 | Login | Response body contains an access token and **no** refresh token; `Set-Cookie: __Secure-is_refresh=...; HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth; Max-Age=604800` | RT-02, RT-03 (A-08) |
| G1-RT-02 | Refresh token value | At least 43 URL-safe characters (256 bits); two logins give different values | RT-01 |
| G1-RT-03 | Database after login | `refresh_tokens.token_hash` is the SHA-256 of the cookie value; the plaintext appears in no column | RT-01 (A-08) |
| G1-RT-04 | `POST /auth/refresh` with a valid cookie and `X-Requested-With: IntelliStudy` | 200; new access token; new cookie with a different value; old row `rotated` with `replaced_by_id` = new row; same `family_id` | RT-04 (A-04) |
| G1-RT-05 | **Reuse:** refresh with token T1 (succeeds, issues T2), then refresh again with T1 | Second call: 401, cookie cleared, **every** token of the family revoked (`reuse_detected`); a refresh with T2 now also fails; security event `refresh_reuse` | RT-05 (A-05) |
| G1-RT-06 | **Race:** two concurrent refresh calls with the same T1 | Exactly one succeeds; the other is treated as reuse and revokes the family (no grace window) | RT-04, RT-05 |
| G1-RT-07 | Refresh with a revoked token (after logout) | 401; cookie cleared | RT-06 (A-06) |
| G1-RT-08 | Idle expiry: advance the clock 7 days + 1 s after the last rotation | 401 | RT-03 |
| G1-RT-09 | Absolute expiry: keep rotating every 6 days; at 30 days + 1 s after login | 401 even though the latest token is within its idle lifetime | RT-03 |
| G1-RT-10 | `POST /auth/logout` | Whole family revoked; cookie cleared (`Max-Age=0`); other families (other devices) still work | RT-06 (A-06) |
| G1-RT-11 | `POST /auth/logout-all` | All of the user's families revoked; `tokens_valid_after` set, so existing access tokens fail (G1-JWT-13) | RT-06 |
| G1-RT-12 | `POST /auth/change-password` | All families revoked and access tokens invalidated, as G1-RT-11; the caller receives a fresh session | RT-06, JWT-05 |
| G1-RT-13 | Refresh **without** `X-Requested-With: IntelliStudy` | 403; token not rotated | RT-07 (A-07) |
| G1-RT-14 | Refresh / logout with `Origin: https://evil.example` | 403; token not rotated | RT-07, HTTP-02 (A-07) |
| G1-RT-15 | Refresh with no cookie; with a random cookie value; with a cookie on the wrong path | 401 | RT-04 |
| G1-RT-16 | Refresh for a locked or disabled account | 401 | RT-08 (A-10) |
| G1-RT-17 | Logs and response bodies during G1-RT-01..16 | Refresh-token values never appear | RT-01, RT-02, SEC-06 (A-08) |
| G1-RT-18 | 31 refreshes within one hour by one user | The 31st returns 429 with `Retry-After` | 9a (S-11) |
